## 드랍쉽핑 로컬 프로그램 추가 기능 조사 보고서

기존 설계(상품 동기화 · 미리보기 · 주문 발주 · 리스팅 · 댓글 답글)를 기준으로, 2025~2026년 공개된 CJ Dropshipping API·Shopify GraphQL·WooCommerce 생태계 및 상용 드랍쉽핑 자동화 도구들의 기능을 조사했습니다. 결론부터 말하면, **기존 5개 기능은 "실행"에 해당하고, 실제 운영에서 살아남으려면 그 앞뒤에 있는 6개 계층—가격/운임, 재고 라우팅, 웹훅, 사후 처리(분쟁·반품), 수익성 분석, 알림/모니터링—이 추가로 필요**합니다.

---

### 1. 가격 결정 엔진 — 공급가 + 운임 + 마크업

기존 설계에는 “가격을 그대로 전송”하는 부분만 있고, **얼마에 팔 것인지**를 계산하는 계층이 없습니다. 상용 도구들은 예외 없이 이 계층을 핵심 기능으로 내세웁니다.

Importify는 **고정 또는 비율 기반 마진에 사용자 정의 반올림을 적용하는 유연한 가격 마크업 규칙**과 실시간 환율 반영을 제공합니다. PriceMole은 “공급가보다 30% 높게”, “최저 경쟁사보다 $0.5 낮게”, “평균가 매칭”, “가장 수익성 높은 가격 추천” 같은 **전략 프리셋**을 제공하고, 경쟁사 가격을 자동 추적해 번들 가격에 반영합니다. `dropship-cli`는 `dropship price` 명령으로 전체 상품 가격을 최적화하고, `dropship supplier`로 실제 CJ 가격 기반 공급처 분석을 수행합니다.

**추가해야 할 모듈:**

- `PricingRule`: `(supplier_price + freight) × (1 + margin) + fixed_fee` 형태의 계산식, 통화별 반올림 규칙
- `ExchangeRateService`: 환율 캐시 및 변동 임계치 초과 시에만 가격 재계산
- `CompetitorPriceProvider`: 경쟁사 가격 수집(스크래핑 또는 수동 입력) 및 최저가/평균가 전략
- `PriceGuard`: 마진이 설정 하한 이하로 떨어지면 가격 인상을 보류하고 알림

이 계층이 없으면 공급가 인상이나 환율 변동이 발생할 때마다 **마이너스 마진 상품이 조용히 팔립니다**.

---

### 2. 운임 계산과 배송 추정 — CJ `calculate_freight`

CJ API는 **상품별 물류 운임 계산(`calculate_freight`)과 목적지별 물류 소요시간 조회(`get_logistics_timeliness`), 가용 창고 목록 조회(`get_warehouses`)** 를 공식 도구로 제공합니다. CJ는 각 노선에 대해 운임과 배송 시간을 견적하며, 이 배송 시간이 상품의 배송 예정일이 됩니다. 운임은 “예상 배송비 포함” 가격 규칙으로 회수할 수 있습니다.

**추가해야 할 모듈:**

- 상품 업로드 시 **목적지별 운임을 미리 계산해 마크업에 반영**하는 `FreightEstimator`
- `get_warehouses` 결과를 로컬에 캐싱해 **재고가 있는 창고만 후보로** 주문 라우팅에 전달
- 운임 변동이 큰 상품은 **무료배송 임계치** 또는 **별도 배송비 정책**으로 분리

기존 설계의 `build_cj_payload`는 `logisticName`을 하드코딩하거나 주문에서 가져오는 수준이었는데, 여기에 **목적지·중량·창고별 최적 물류사 선택** 로직을 추가해야 합니다.

---

### 3. 주문 라우팅과 다중 공급처 — “어디서 살 것인가”

DSers의 핵심 기능은 **들어오는 주문을 구매 시점에 최저가 또는 최적 재고를 가진 공급처로 자동 라우팅**하는 것입니다. Nventory는 고객 주문 시 **규칙에 따라 올바른 공급처로 구매 주문(PO)을 자동 생성**합니다. Shopify는 2025-10 버전에서 **`fulfillmentOrdersReroute` 뮤테이션**을 추가해 주문을 다른 이행 위치로 재라우팅할 수 있게 했습니다.

기존 설계는 `mapping` 테이블에 `priority` 컬럼만 두고 사실상 단일 공급처를 가정했습니다. 여기에 다음이 필요합니다.

- **공급처별 실시간 견적 비교**: CJ `calculate_freight` + 변형 가격 + 재고를 조합해 주문 시점 최적 공급처 선택
- **대체 공급처 자동 전환**: 1순위 공급처 재고 0 또는 리드타임 초과 시 2순위로 자동 전환
- **Shopify `fulfillmentOrdersReroute` 연동**: 창고가 여러 개인 경우 주문을 가장 가까운/빠른 위치로 재라우팅
- **다중 스토어 지원**: CJ 플러그인 사례처럼 스토어별 개별 자격 증명으로 여러 스토어를 관리하는 구조

---

### 4. 웹훅 기반 실시간 동기화 — 폴링의 한계를 보완

CJ 공식 웹훅 문서에 따르면, CJ는 **`product`, `stock`, `order`, `logistics`, `makeup`, `privateOrder`, `dispute` 7개 토픽**을 지원합니다. 각 토픽은 `ENABLE`/`CANCEL`로 설정하며, **콜백 URL은 하나만 지원되고 반드시 공개 HTTPS 주소**여야 합니다. `localhost`와 `127.0.0.1`은 허용되지 않으며, **응답은 3초 이내**에 200을 반환해야 합니다.

이 제약은 로컬 프로그램에 직접적인 영향을 줍니다. **로컬에서 웹훅을 받으려면 ngrok·Cloudflare Tunnel 같은 터널링이 필수**입니다. 또는 웹훅 수신 전용 경량 서버를 클라우드에 두고, 로컬 프로그램이 그 서버의 큐를 폴링하는 **릴레이 구조**를 쓰는 편이 안정적입니다.

CJ 웹훅 설정에는 함정이 하나 있습니다. **`webhook/set` 호출 시 4개 토픽(`product`, `stock`, `order`, `logistics`)을 매번 모두 포함해야 하며, `enable()`하지 않은 토픽은 `CANCEL`로 전송되어 비활성화**됩니다. 즉, `stock`만 켜려고 호출하면 나머지 3개가 꺼질 수 있으므로, **항상 7개 토픽 전체를 현재 원하는 상태로 구성해 한 번에 전송**해야 합니다.

**추가해야 할 모듈:**

- `WebhookRelay`: 터널 또는 클라우드 릴레이를 통한 CJ 웹훅 수신, 서명/출처 검증
- `WebhookRouter`: `stock` 이벤트는 재고 동기화 큐로, `order`/`logistics`는 주문 상태 업데이트로, `dispute`는 사후 처리 워크플로로 라우팅
- **3초 응답 규칙 준수**: 수신 즉시 200을 반환하고, 실제 처리는 백그라운드 워커로 위임

웹훅이 없으면 재고 동기화 주기(15~60분) 동안 오버셀이 발생할 수 있습니다. **웹훅(인바운드) + 폴링(보정)** 이중 구조가 정석입니다.

### 5. 사후 처리 — 분쟁·반품·환불 자동화

CJ는 **분쟁(dispute) API**를 제공합니다. 절차는 **① 분쟁 가능 상품 목록 조회 → ② 분쟁 확인(사유·금액 정보) → ③ 분쟁 생성** 순서이며, 대상은 주문 상품의 **환불 및 재배송(보충)** 입니다. CJ 정책상 상품이 창고에서 처리되기 전에는 전액 환불이 가능하고, 부분 파손 시 부분 환불 또는 교체가 가능합니다. 또한 CJ는 **국내 창고 보관(localized domestic warehouse returns)** 옵션을 제공하므로, 반품을 로컬 3PL 주소로 받는 구조도 설계할 수 있습니다.

`dropship-cli`는 `dropship returns`로 반품·환불을 처리하고, `dropship guard`로 **수익 보호 스캔**을 수행합니다. Commerce OS 사례에서는 **모든 결제·환불에 주문별/일별 한도를 둔 spend guard 승인**을 요구하고, 공급처·마켓플레이스 쓰기를 **멱등(idempotent)** 으로 만들어 **이중 주문·이중 환불을 방지**합니다.

**추가해야 할 모듈:**

- `DisputeService`: 분쟁 가능 상품 조회 → 사유/금액 확인 → 분쟁 생성의 3단계 파이프라인
- `RefundGuard`: 주문별·일별 환불 한도, 이중 환불 방지(멱등 키)
- `ReturnRouter`: 반품을 CJ 국내 창고로 보낼지, 폐기 후 재배송할지 결정하는 규칙
- **분쟁 상태 추적**: `dispute` 웹훅 또는 폴링으로 결과(환불/재배송/거절)를 로컬 DB에 기록

기존 설계에는 주문 생성 이후의 **실패 경로**가 없었습니다. 드랍쉽핑에서 실제 CS 문의의 대부분은 배송 지연·파손·미배송이므로, 이 계층이 없으면 주문 발주 자동화의 효과가 절반으로 줄어듭니다.

---

### 6. 수익성 분석과 공급처 성과 — “남는 장사인가”

`dropship-cli`는 `dropship profit`으로 실제 P&L을, `dropship analyze`로 비즈니스 분석 리포트를, `dropship forecast`로 매출·재고 예측을, `dropship segment`로 RFM 고객 세분화를 제공합니다. Base Connect는 **공급처별 성과·배송 시간·수익성·환불 비율**을 분석합니다. MerchantFlow는 CJ의 실제 이행·배송 비용을 P&L에 끌어와 추정치가 아닌 실측치로 계산합니다.

기존 설계의 DB에는 `orders.total`과 `order_items.unit_price`만 있고, **실제 원가(공급가 + 운임 + 수수료 + 환불)** 가 없습니다. 따라서 “이 주문이 얼마를 남겼는가”를 계산할 수 없습니다.

**추가해야 할 모듈:**

- `CostLedger`: 주문별 공급가(CJ) + 운임(CJ 견적) + 채널 수수료 + 환불/분쟁 금액을 **이중 기장(double-entry)** 으로 기록
- `ProfitReport`: SKU별·공급처별·채널별 마진, 환불률, 리드타임
- `SupplierScorecard`: 공급처별 평균 배송 시간, 분쟁률, 재고 안정성 점수 → 주문 라우팅 우선순위에 피드백
- **환율 반영**: 다통화 주문의 경우 결제 통화와 정산 통화 차이를 기록

---

### 7. 재고 소진 예측과 자동 리스팅 제어

CJ WooCommerce 플러그인은 **CJ SKU가 품절되면 채널에서 판매 불가로 전환해 오버셀을 방지**하는 자동 재고 동기화를 강조합니다. Shopify는 **2026-04 버전에서 `tracks_inventory` 불리언 필터**를 추가했는데, 이는 **재고를 직접 보유하지 않는 드랍쉽퍼**에게 특히 유용하다고 명시되어 있습니다. Shopify Flow 2025-10은 **재고 생성·입고·출고 타임스탬프(`dateCreated`, `dateReceived`, `dateShipped`)** 를 제공해 재고 사이클을 정밀 추적할 수 있게 했습니다.

**추가해야 할 모듈:**

- `StockoutPredictor`: 최근 판매 속도와 공급처 리드타임을 결합해 **재고 소진 예상일** 계산, 임계 이하 시 리스팅 자동 숨김 또는 안전 재고 알림
- `InventoryTimestampTracker`: Shopify의 재고 타임스탬프를 활용해 **입고 지연 공급처 식별**
- `AutoHideRule`: 재고 0 + 백오더 불가 시 `catalog_visibility=hidden`(Woo) / `publishableUnpublish`(Shopify) 자동 실행

---

### 8. 고객 지원 인박스 — 리뷰 답글을 넘어서

기존 설계는 “댓글 답글”에 한정되어 있었습니다. 그러나 드랍쉽핑 CS의 실제 볼륨은 **배송 조회, 주소 변경, 반품 요청, 분쟁 문의**가 대부분입니다. `dropship-cli`는 `dropship support`로 고객 티켓을 처리하고, `dropship reviews`로 리뷰 분석·평판 관리를 수행합니다. Zendesk AI는 티켓 정리·자동 응답·반복 티켓 감소를 제공합니다.

**추가해야 할 모듈:**

- `SupportInbox`: 채널 주문 메모(Woo `order notes`, Shopify `order timeline`), 리뷰, 이메일 문의를 **하나의 로컬 큐**로 통합
- `TicketClassifier`: 배송 조회 / 반품 / 주소 변경 / 분쟁 / 일반 문의로 자동 분류
- `AutoResponder`: 배송 추적 번호·CJ 주문 상태를 조회해 **1차 자동 응답 초안** 생성, 사람이 승인 후 발송
- `ReviewAnalyzer`: 리뷰 감성·키워드 분석으로 **상품 개선 피드백**과 **공급처 품질 이슈**를 조기 감지

특히 **WooCommerce 리뷰 답글의 인증 분리**는 이미 지적한 대로 중요합니다. 리뷰 조회는 WooCommerce 키(`ck_`/`cs_`)로 가능하지만, 답글 작성은 **WordPress Application Password**(사용자 프로필 → Application Passwords)로 인증해야 합니다.

### 9. AI 보조 — 상품 소싱·카피라이팅·운영 어시스턴트

CJ는 공식 **MCP(Model Context Protocol) 서버**를 제공합니다. 이를 통해 ChatGPT·Claude 같은 AI 클라이언트가 자연어로 **상품 검색, SKU 상세 조회, 주문 목록, 운임 계산, 물류 소요시간, 창고 목록, 분쟁 목록·상세·생성, 주문 병합** 등의 도구를 직접 호출할 수 있습니다. `dropship-cli`는 아예 “Claude Code처럼 터미널에서 드랍쉽핑 비즈니스를 운영하는” 컨셉으로, `scout`(트렌드 상품 탐색), `source`(CJ에서 소싱해 Shopify로 임포트), `copy`(AI 카피라이팅), `autopilot`(15분마다 전체 에이전트 오케스트레이션)을 제공합니다.

**추가해야 할 모듈:**

- `MCPBridge`: CJ MCP 서버를 로컬 프로그램의 도구 레이어로 연결해, “이 SKU의 EU 운임과 리드타임을 알려줘” 같은 질의를 코드 없이 처리
- `ProductResearchAgent`: CJ 카탈로그에서 판매량·리뷰·운임을 기준으로 후보 상품 스코어링
- `CopyOptimizer`: 상품 제목·설명·이미지 순서를 AI로 최적화하되, **원본 공급처 설명을 그대로 복사하지 않도록** 중복 콘텐츠 검사

단, AI가 생성한 가격·답글·설명은 **반드시 사람 승인 게이트**를 거치도록 설계해야 합니다. `dropship-cli`도 `autopilot` 외 명령은 개별 실행 방식이며, 금전이 걸린 발주·환불은 자동화 범위에서 분리하는 것이 안전합니다.

---

### 10. 규정·관세 — EU/UK 판매 시 선택이 아닌 필수

국제 드랍쉽핑에서 **landed cost(도착지 총비용)** 를 표시하지 않으면 관세·부가세로 인한 반품·차지백이 급증합니다. WooCommerce에는 **ePAL Cross Border Calculator**가 있어 상품 분류·VAT·관세·배송 관련 세금을 체크아웃에서 계산하고, **IOSS와 관세 처리 방식을 비교**합니다. Shopify에는 **Zonos Duty and Tax**, **Tax & Duty King**이 있어 HS 코드·IOSS·DDP·다중 원산지 이행을 지원합니다. EAS EU compliance는 EU·UK VAT와 관세 컴플라이언스를 자동화합니다.

로컬 프로그램에 직접 관세 계산 엔진을 넣는 것은 현실적이지 않습니다. 대신 **채널 앱(Shopify/Woo 플러그인)에 위임하고, 로컬 프로그램은 HS 코드·원산지·중량 메타데이터를 상품에 정확히 채워 넣는 역할**을 하는 것이 효율적입니다.

---

### 11. 운영 안전장치 — 멱등성·알림·헬스체크

조사한 상용 도구들이 공통적으로 강조하는 운영 안전장치는 다음과 같습니다.

- **멱등성**: 공급처·마켓플레이스 쓰기를 멱등하게 만들어 이중 주문·이중 환불 방지. 기존 설계의 `cj_orders.local_order_id UNIQUE` 제약을 **모든 외부 쓰기(분쟁, 환불, 리스팅 게시/비게시)로 확장**해야 합니다.
- **Spend Guard**: 주문별·일별 결제/환불 한도와 승인 게이트.
- **알림**: `dropship-cli notify`는 Slack/Discord 알림을 설정합니다. 재고 소진, 발주 실패, 분쟁 생성, 웹훅 수신 중단을 알림으로 승격해야 합니다.
- **헬스체크**: `dropship doctor`는 시스템 건강 상태를 점검합니다. 토큰 만료, 웹훅 미수신, 큐 적체, API 오류율을 주기적으로 확인하는 `HealthCheck`가 필요합니다.
- **감사 로그**: CJ 플러그인은 전체 감사 추적(activity logging)을 제공합니다. 모든 외부 API 호출과 상태 변경을 로컬에 기록해야 분쟁 시 근거가 됩니다.

### 12. Shopify·WooCommerce API 변화 대응

- **Shopify는 GraphQL 우선**으로 전환되었고, Winter 2025 에디션에서 GraphQL API 개선과 REST→GraphQL 전환 문서가 강조되었습니다. 기존 설계가 GraphQL 기반인 것은 맞지만, **API 버전을 `2025-10` 이상으로 고정**하고 `2026-04`의 `tracks_inventory` 필터를 드랍쉽핑 상품 필터링에 활용할 수 있습니다.
- **Shopify Flow 2025-10**의 `fulfillmentOrdersReroute`는 로컬 프로그램의 주문 라우팅과 **중복 기능**이 될 수 있습니다. 로컬에서 라우팅 결정을 내리되, Shopify 측 이행 위치 변경은 `fulfillmentOrdersReroute`로 실행하는 **역할 분담**이 효율적입니다.
- **WooCommerce**는 배치 API(최대 100개)와 주문 노트·환불 API를 제공하므로, 기존 설계의 배치 업데이트 구조를 유지하되 **환불(`refunds`)와 주문 노트를 사후 처리 모듈에 연결**해야 합니다.

### 우선순위 제안

| 순위 | 기능 | 이유 |
|---|---|---|
| **P0** | 가격 결정 엔진 + 운임 계산 | 없으면 마이너스 마진 판매가 발생 |
| **P0** | 웹훅 릴레이 + 재고 실시간 동기화 | 폴링만으로는 오버셀 방지 불가, CJ 웹훅은 공개 HTTPS 필수 |
| **P1** | 분쟁·반품·환불 파이프라인 | 주문 발주 후 실제 CS 볼륨의 대부분 |
| **P1** | 수익성 원가 장부(Cost Ledger) | “남는 장사인지” 판단 불가능한 상태 탈피 |
| **P2** | 주문 라우팅·다중 공급처 | 공급처 장애·품절 시 매출 손실 최소화 |
| **P2** | 고객 지원 인박스 + 리뷰 분석 | 리뷰 답글을 넘어선 통합 CS |
| **P3** | AI 소싱·카피라이팅·MCP 연동 | 효율 향상이지만 없어도 운영 가능 |
| **P3** | 관세·VAT/IOSS | EU/UK 판매 비중이 높을 때 필수, 채널 앱 위임 권장 |

기존 5개 기능은 **“주문을 넣고 상품을 올리는” 실행 계층**이었습니다. 조사 결과가 말하는 것은, 드랍쉽핑 자동화의 실제 경쟁력은 **가격·운임·재고·사후 처리·수익성**이라는 **판단·보호 계층**에서 나온다는 점입니다. 이 계층을 추가하면 로컬 프로그램은 “API 커넥터”에서 **운영 콘솔**로 완성됩니다.
