## 드랍쉽핑 로컬 프로그램 추가 보안사항 보고서

이 프로그램은 **금전(주문·환불), 개인정보(배송지·연락처), 채널 자격 증명(Admin Token), 공급처 자격 증명(openId)** 을 동시에 다루는 로컬 애플리케이션입니다. 로컬에서 돈다는 사실은 보안 부담을 줄여주지 않습니다. 오히려 **웹훅 수신을 위한 터널 노출, `.env` 파일의 디스크 상주, SQLite 평문 저장**이라는 로컬 특유의 위험을 추가합니다. 아래는 기존 설계에 반드시 추가해야 할 보안 계층입니다.

---

### 1. 자격 증명 관리 — “코드 밖, Git 밖, 짧은 수명”

가장 빈번한 침해 경로는 취약점 공격이 아니라 **유출된 자격 증명으로 정상 로그인하는 것**입니다. 하드코딩된 API 키와 Git에 커밋된 `.env` 파일은 여전히 Python 앱에 침입하는 가장 빠른 경로입니다.

**보관 위치의 계층**은 다음과 같이 강제해야 합니다: 소스 코드 하드코딩(절대 금지) → Git에 커밋된 `.env`(절대 금지, 히스토리에 영구 잔존) → **커밋되지 않은 `.env` + `.gitignore`**(로컬 개발 허용) → **전용 시크릿 매니저**(프로덕션 권장).

```python
# config.py — 시크릿 누락 시 즉시 실패, 기본값 금지
import os

class Config:
    def __init__(self):
        self.wc_ck = os.environ["WC_CK"]          # 기본값을 절대 두지 않는다
        self.wc_cs = os.environ["WC_CS"]
        self.shopify_token = os.environ["SHOPIFY_TOKEN"]
        self.cj_open_id = os.environ["CJ_OPEN_ID"]   # 웹훅 서명 키도 포함
```

`os.environ.get("SECRET", "dev-secret-123")` 같은 **기본값은 개발용 플레이스홀더가 프로덕션 트래픽을 인증하는 사고**로 이어집니다. 시크릿은 시작 시 환경에서 읽고 누락되면 **크래시**하는 편이 낫습니다.

**DSers의 OAuth 2.1 + PKCE 사례는 좋은 참조 모델입니다.** DSers는 MCP 클라이언트 설정에 **비밀번호·API 키·스토어 토큰·브라우저 쿠키·수동 복사한 `Authorization` 헤더를 붙여넣지 말 것**을 명시하고, 서버 URL만 등록한 뒤 브라우저 OAuth 플로우로 인증합니다. 로컬 프로그램도 CJ·Shopify·WooCommerce 자격 증명을 **설정 파일에 평문으로 두지 않고**, 가능하면 OAuth 또는 앱 비밀번호 발급 플로우를 사용하는 것이 바람직합니다.

**시크릿 스캐너를 pre-commit 훅으로** 반드시 추가하세요. `gitleaks`를 pre-commit에 걸면 키가 커밋에 도달하기 전에 차단할 수 있고, 이미 유출된 키는 전체 Git 히스토리를 스캔해 탐지해야 합니다.

### 2. 웹훅 보안 — CJ·Shopify·WooCommerce 모두 “서명 검증”이 필수

웹훅 엔드포인트는 **누구나 POST할 수 있는 공개 진입점**입니다. 서명 검증 없이 본문을 신뢰하면 공격자가 가짜 재고·주문·배송 이벤트를 주입해 시스템 상태를 조작할 수 있습니다.

#### CJ — `openId`가 계정 식별자이자 HMAC 비밀키

CJ는 웹훅 요청의 `sign` 헤더에 **HMAC-SHA256(secret=openId, message=raw body, Base64)** 서명을 담아 보냅니다. 검증 절차는 ① `sign` 헤더 읽기 → ② **원본 바이트 그대로** 읽기(역직렬화 후 재직렬화하면 필드 순서가 달라져 서명이 깨짐) → ③ `openId`를 secret으로 HMAC 계산 → ④ Base64 인코딩 후 문자열 비교입니다.

**가장 위험한 설계상의 함정은 `openId`의 이중 역할**입니다. CJ 문서는 `openId`가 **계정 식별자이면서 동시에 웹훅 서명 비밀키**라고 명시하며, **웹훅 수신 URL·원본 페이로드·`openId`가 포함된 로그나 스크린샷을 제3자(통합 업체, ERP 플러그인, 디버깅 도구)에게 절대 공유하지 말 것**을 경고합니다. `openId`가 유출되면 **CJ를 사칭한 유효한 서명을 위조**할 수 있습니다. 따라서 `openId`는 API 토큰과 동급으로 취급하고, 로그에서 반드시 마스킹해야 합니다.

```python
# webhook/cj_verify.py
import hmac, hashlib, base64

def verify_cj(raw_body: bytes, sign_header: str, open_id: str) -> bool:
    expected = base64.b64encode(
        hmac.new(open_id.encode(), raw_body, hashlib.sha256).digest()
    ).decode()
    return hmac.compare_digest(sign_header, expected)
```

#### Shopify — `X-Shopify-Hmac-SHA256`, Base64, timing-safe

Shopify는 앱의 **client secret**을 키로 원본 요청 바디에 HMAC-SHA256을 적용하고, 결과를 **Base64**(hex 아님)로 인코딩해 `X-Shopify-Hmac-SHA256` 헤더로 보냅니다. 검증은 ① 원본 바디 사용(JSON 파서 통과 후 재직렬화 금지) → ② Base64 디코드 → ③ **`crypto.timingSafeEqual` 상당의 타이밍 안전 비교** 순서입니다. Shopify 문서는 **모든 웹훅을 처리 전에 HMAC 검증**하고, 개발용 모의 도구 외에는 검증을 생략하지 말 것을 강조합니다.

또한 Shopify는 **delivery ID로 중복 배송을 탐지**하라고 명시합니다. 웹훅은 재전송될 수 있으므로, `X-Shopify-Webhook-Id`를 로컬 DB에 기록해 **동일 이벤트를 두 번 처리하지 않도록** 해야 합니다.

#### WooCommerce — `X-WC-Webhook-Signature`

WooCommerce는 웹훅 설정 시 지정한 **secret**으로 원본 바디의 HMAC-SHA256을 계산해 **Base64**로 인코딩하고 `X-WC-Webhook-Signature` 헤더에 담습니다. FastAPI 핸들러에서는 `request.body()`로 **원본 바이트**를 받아 `hmac.compare_digest`로 비교해야 합니다. Express 진영에서도 “raw body 파서를 사용하라”는 점이 반복적으로 강조됩니다.

**세 채널 모두 공통 규칙:** 서명 검증은 **파싱 전에** 수행하고, 비교는 **타이밍 안전**하게 하며, 원본 바디를 사용해야 합니다.

### 3. 로컬 웹 서버와 터널 — “루프백에 바인딩하라”

미리보기·발주 승인 UI를 FastAPI로 로컬에서 띄우면, 기본 설정에 따라 **`0.0.0.0`에 바인딩되어 같은 네트워크의 다른 기기에서 접근 가능**해질 수 있습니다. 특히 웹훅 수신을 위해 ngrok·Cloudflare Tunnel 같은 터널을 연결하면 위험이 커집니다.

**역프록시 루프백 우회 취약점**이 실제로 보고되었습니다. OpenClaw Gateway 사례에서 게이트웨이가 리버스 프록시(Tailscale Funnel, nginx, Cloudflare Tunnel, ngrok) 뒤에 있을 때, 프록시가 **루프백으로 연결**하기 때문에 **설정된 웹훅 비밀번호를 우회한 비인증 원격 요청**이 가능해졌습니다. 교훈은 명확합니다. **터널이 활성화된 경우 웹훅 서버를 `0.0.0.0`이 아니라 `127.0.0.1`에 바인딩**해야 하며, 외부 트래픽은 터널을 통해서만 들어오게 해야 합니다.

**FastAPI 로컬 서버 최소 보안 요건:**

- **API 키 또는 Bearer 토큰 인증**: `/api/*` 경로에 `APIKeyHeader` 또는 미들웨어로 키 검증을 강제합니다. 키는 환경변수/시크릿 매니저에서 읽고, **단방향 해시로 저장**하며, 발급·검증·폐기·회전·감사 기능을 갖춘 라이브러리(`keyguard`, `safe-api-keys` 등)를 활용할 수 있습니다.
- **바인딩 주소**: 터널 사용 시 `127.0.0.1`, 터널 미사용 시에도 가급적 루프백. `0.0.0.0`은 명시적으로 필요한 경우에만.
- **TLS**: 로컬이라도 민감 데이터를 다루므로 터널 구간은 TLS 1.2+ 를 강제합니다. CJ도 웹훅에 **HTTPS와 TLS 1.2/1.3**을 요구합니다.
- **디버그 엔드포인트 비활성화**: `/docs`, `/redoc`, `/openapi.json`은 로컬에서도 인증 뒤에 두거나 프로덕션 모드에서 비활성화합니다. OWASP는 **보안 설정 오류(API8)** 의 대표 사례로 디버그 엔드포인트와 CORS 와일드카드를 지목합니다.
- **최소 노출 시간**: 터널은 웹훅 테스트·수신에 필요한 시간만 열고, 상시 개방하지 않습니다.

### 4. 로컬 데이터베이스 — SQLite는 기본적으로 암호화되지 않는다

SQLite는 **내장 암호화를 제공하지 않습니다**. 데이터베이스 파일을 열면 **모든 행과 열이 평문으로 읽힙니다**. 파일 수준 접근 제어도 없습니다. 주문·배송지·연락처·리뷰가 들어가는 DB를 평문으로 두면, 노트북 분실·백업 유출·악성코드가 곧 개인정보 유출로 이어집니다.

**선택지:**

- **SQLCipher 기반 암호화**: `sqlcipher3` 또는 SQLCipher를 번들한 드라이버로 DB 전체를 AES-256 암호화합니다. 암호화 키는 **소스 코드 밖**에 두고, 강력한 무작위 키를 사용하며, DB 파일을 **공개 웹 디렉터리에 노출하지 않아야** 합니다.
- **필드 수준 암호화**: 전체 DB 암호화가 부담이면, 최소한 **배송지·연락처·이메일·고객 이름**을 AES-GCM 또는 AES-SIV로 필드 암호화합니다. `floorvault` 같은 라이브러리는 **테이블·레코드·컬럼·스키마에 바인딩된 암호문**을 만들어, 암호문을 다른 위치로 옮기면 복호화가 실패하도록 합니다.
- **파일 권한**: DB 파일과 WAL/SHM 파일의 권한을 `600`으로 제한하고, 백업도 동일하게 암호화합니다.

**중요:** DB 암호화는 만능이 아닙니다. 애플리케이션이 탈취되면 복호화 키도 함께 탈취될 수 있습니다. 따라서 **키를 DB와 분리**하고, 가능하면 OS 키체인 또는 시크릿 매니저에서 런타임에 가져오세요.

### 5. 로깅 — 민감 정보는 “기록 전에” 마스킹한다

시크릿은 정문이 아니라 **옆문으로 유출**됩니다. 전체 요청 로그, 설정 객체를 직렬화한 예외 메시지, 환경변수 디버그 덤프가 대표적입니다. 특히 **CJ `openId`는 웹훅 서명 키이므로 로그에 남으면 즉시 위조 가능**해집니다.

**규칙:**

- **API 키·토큰·`openId`·`Authorization` 헤더·쿠키·세션 토큰은 절대 원문 기록 금지**. 앞 4자리 + `***` 수준의 **식별 가능한 부분 마스킹**을 적용합니다.
- **PII(이메일·전화번호·주소·카드번호)** 는 로그 포맷터 단계에서 자동 마스킹합니다. `pii-safe-logger`, `hushlog`, `jsonmask` 같은 라이브러리는 커스텀 필드·정규식·부분 마스킹을 지원하며, JSON 로그의 중첩 구조까지 처리합니다. `logging.Filter`를 루트 로거에 설치해 **디스크나 stdout에 PII가 쓰이기 전에** 변이시키는 방식도 효과적입니다.
- **프로덕션에서 프레임워크 디버그 모드 비활성화**: 대화형 트레이스백은 지역 변수에 담긴 시크릿을 그대로 노출합니다.
- **웹훅 원본 페이로드 보관 시 주의**: 디버깅을 위해 원본을 저장하더라도 `openId`·서명 헤더·배송지가 포함될 수 있으므로 **암호화 저장 + 보존 기간 제한**을 적용합니다.

### 6. 감사 로그 — “누가 무엇을 바꿨는가”를 위조 불가능하게

주문 발주·환불·리스팅 게시/비게시는 **금전과 노출에 직접 영향**을 줍니다. 사고 발생 시 “누가 언제 무엇을 바꿨는가”를 증명할 수 있어야 합니다.

**해시 체인 기반 감사 로그**를 권장합니다. 각 이벤트를 **append-only**로 기록하고, 이전 이벤트의 해시를 포함시켜 체인을 구성하면, 과거 항목이 수정될 경우 **이후 모든 항목의 암호학적 유효성이 깨집니다**. `merkle-audit` 같은 도구는 AI 에이전트의 도구 호출(웹 검색, 파일 쓰기, API 호출, 결제)을 이런 방식으로 기록합니다.

**감사 대상:** 주문 생성·취소·환불, CJ 발주 생성, 송장 푸시, 리스팅 게시/비게시, 리뷰 답글 발송, 가격 규칙 변경, 자격 증명 교체. 각 이벤트에는 **행위자, 시각, 대상 리소스 ID, 변경 전/후 상태, 요청 ID**를 포함합니다.

DSers의 안전 모델도 참고할 만합니다. 도구를 **읽기(read) / 쓰기(write) / 위험(dangerous)** 으로 분류하고, 상태 변경 워크플로에는 **정확한 리소스 식별자, 소유권 검사, OAuth 스코프, 오래된 상태 검사, 위험 호출 전 명시적 사용자 확인**을 요구합니다. **상위 완료가 불확실한 쓰기는 재시도 불가(non-retryable)로 보고**하고, 클라이언트는 자동 재시도 대신 **현재 상태를 조사**해야 합니다. 이 원칙은 주문 발주·환불에 그대로 적용해야 합니다.

### 7. 의존성 공급망 — `pip install`은 더 이상 무해하지 않다

2026년 PyPI 생태계는 **타이포스쿼팅(typosquatting), 의존성 혼동(dependency confusion), 유지관리자 계정 탈취**의 지속적인 표적입니다. 악성 패키지는 CI/CD 파이프라인을 노려 **정보 탈취 페이로드**를 심습니다. 2026년 3월에는 LiteLLM의 PyPI 배포 자격 증명이 **CI/CD에서 오염된 Trivy 스캐너**를 통해 탈취되어 악성 버전이 배포된 사례도 있습니다.

**방어:**

- **정확한 버전 + 해시 고정**: `requirements.txt`에 `==`로 버전을 고정하고, **`--require-hashes`** 로 패키지 해시까지 검증합니다. 인덱스를 신뢰할 수 있는 소스로 제한하고 **fallback 인덱스를 비활성화**해 의존성 혼동을 차단합니다.
- **`pip-audit` / Snyk / Dependabot**을 CI 또는 pre-commit에 통합해 알려진 취약점과 악성 패키지를 탐지합니다.
- **잠금 파일**(`pip-tools`, `uv lock`, `poetry.lock`)을 사용하고, 새 의존성 추가 시 **패키지 이름·유지관리자·다운로드 수·저장소**를 수동 검토합니다.
- **가상환경 격리** 및 최소 권한 실행(DB 파일·네트워크 접근 범위 제한).

### 8. 개인정보·결제 규정 — GDPR과 PCI DSS

#### GDPR

드랍쉽핑은 공급처가 EEA 밖에 있는 경우가 많아 **국경 간 데이터 이전**이 발생합니다. GDPR 제32조는 드랍쉽퍼와 공급처 모두 **처리의 성격·범위·목적에 맞는 기술적·조직적 조치**를 요구합니다. EU/UK 고객에게 판매한다면 **EU 대표자(Article 27)** 지정 의무가 있을 수 있습니다.

**로컬 프로그램에 반영할 사항:**

- **데이터 최소화**: 주문 이행에 필요한 필드만 저장하고, 불필요한 고객 데이터는 수집 즉시 폐기합니다.
- **보존 기간**: 주문·배송지·리뷰 데이터에 **TTL을 설정**하고, 기간 경과 시 자동 삭제 또는 익명화합니다.
- **공급처와의 DPA**: CJ 등 공급처에 고객 PII를 전달하므로 **데이터 처리 계약(DPA)** 과 **표준 계약 조항(SCC)** 이 필요할 수 있습니다. 고객에게는 **이행 파트너와의 데이터 공유 사실을 고지**해야 합니다.
- **프라이버시 바이 디자인**: 로그·DB·백업 전 단계에서 PII를 최소화하고 암호화합니다.

#### PCI DSS

좋은 소식은 **로컬 프로그램이 카드 데이터를 직접 저장·처리하지 않도록 설계**하면 PCI DSS 범위를 크게 줄일 수 있다는 점입니다. 드랍쉽핑 스토어의 결제는 대부분 **채널(Shopify/WooCommerce)과 결제 게이트웨이**가 처리합니다. 로컬 프로그램은 **주문 금액·통화·결제 상태만** 저장하고, **카드 번호·CVV·만료일은 절대 저장하지 않아야** 합니다. 결제 페이지를 **호스팅 결제 페이지(Stripe Checkout, PayPal)** 로 두면 **SAQ-A**(가장 적은 요구사항) 범위를 달성할 수 있습니다.

### 9. OWASP API Security Top 10 매핑 — 로컬 API에도 그대로 적용된다

로컬 FastAPI의 `/api/*`와 각 채널 클라이언트도 API이므로, OWASP API Security Top 10:2025의 주요 위험을 점검해야 합니다.

| OWASP 항목 | 로컬 프로그램에서의 구체적 위험 | 대응 |
|---|---|---|
| **API1 BOLA/IDOR** | `/orders/{id}`에서 `id`만 바꿔 다른 주문 열람 | 세션 소유권 검사, 주문-사용자 매핑 검증 |
| **API2 Broken Auth** | API 키 없이 `/api/*` 접근, 만료 없는 토큰 | API 키/Bearer 필수, 만료·회전·폐기 |
| **API3 BOPLA** | 요청 본문에 `isAdmin`·`price` 필드 주입 | 허용 필드 화이트리스트, 서버 측 가격 재계산 |
| **API4 Unrestricted Resource Consumption** | 대량 주문 조회·중첩 GraphQL 쿼리로 자원 고갈 | 페이지 크기 제한, 쿼리 복잡도 제한, 레이트 리밋 |
| **API7 SSRF** | 공급처 이미지 URL·웹훅 URL에 내부 주소 주입 | URL 화이트리스트, 사설 IP·메타데이터 엔드포인트 차단 |
| **API8 Security Misconfiguration** | `/docs`·`/openapi.json` 공개, CORS `*` | 디버그 비활성화, CORS 오리진 제한 |
| **API10 Unsafe Consumption of APIs** | 공급처 응답을 검증 없이 신뢰 | 응답 스키마 검증, 필드 화이트리스트, 타입·범위 검사 |

특히 **API10**은 드랍쉽핑에서 중요합니다. 공급처 API 응답에 악의적 HTML·스크립트·가격 조작이 섞여 들어올 수 있으므로, **설명(description)은 sanitize 후 저장**하고, **가격·재고는 범위 검사**를 거쳐야 합니다.

### 10. 운영 안전장치 — “실패는 닫히는 방향으로”

- **Fail-closed**: 서명 검증 실패, API 키 불일치, 권한 부족 시 **처리하지 않고 거부**합니다. “검증 실패했지만 일단 처리”는 금지합니다.
- **위험 작업 승인 게이트**: 발주·환불·리스팅 게시/비게시는 **자동 루프에서 분리**하고, 로컬 UI에서 명시적 승인 후 실행합니다. DSers도 **위험 호출 전 사용자 확인**을 요구합니다.
- **불확실한 쓰기의 재시도 금지**: CJ 주문 생성·Shopify fulfillment처럼 **상위 완료가 불확실한 쓰기는 재시도하지 않고** 현재 상태를 조회해 확인합니다. 이는 이중 주문·이중 이행을 막는 핵심입니다.
- **자격 증명 회전**: API 키·웹훅 시크릿·`openId`를 정기적으로 회전하고, **회전 즉시 이전 키를 폐기**합니다. Shopify client secret 회전 시 HMAC 다이제스트가 새 secret으로 생성되기까지 **최대 1시간**이 걸릴 수 있으므로, 회전 중 웹훅 검증이 실패할 수 있는 **유예 창**을 설계해야 합니다.
- **최소 권한**: Shopify Admin API 토큰은 필요한 스코프만 부여하고, WooCommerce 키는 `read/write` 대신 가능하면 `read`부터 시작합니다. CJ API 키도 발주·분쟁 권한과 상품 조회 권한을 분리할 수 있는지 검토합니다.
- **백업 암호화**: SQLite 백업도 **암호화된 상태**로 보관하고, 백업 파일에 자격 증명이 포함되지 않도록 합니다.

| 계층 | 추가 모듈 | 핵심 요건 |

| 운영 | 승인 게이트 + fail-closed + 불확실 쓰기 재시도 금지 | 위험 작업 수동 확인, 이중 실행 방지 |

로컬 프로그램의 보안은 “로컬이니까 안전하다”는 가정이 아니라, **외부에 노출되는 모든 진입점(웹훅, 터널, API)과 디스크에 남는 모든 민감 데이터(자격 증명, PII, DB)** 를 **명시적으로 통제**하는 데서 나옵니다. 특히 **CJ `openId`의 이중 역할**과 **터널 사용 시 루프백 바인딩**은 이 프로그램에서 가장 간과하기 쉬우면서도 치명적인 두 가지 지점입니다.
